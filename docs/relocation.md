# Другой сервер или другой домен

## Новый независимый экземпляр

Выполните [полную установку](deployment.md) с новыми state-каталогами, свежими БД/ключами и собственным доменом. Создайте аккаунты/проекты и настройте источники. Разработчики отдельно входят командой `gitmora auth login --server https://новый-домен` и берут UUID репозиториев из нового экземпляра. UUID старой независимой Gitmora здесь не действуют.

`/install.sh` — установщик клиентского CLI. Он не переносит базу, аккаунты, сертификаты, настройки или сервер Gitmora.

## Перенос существующих данных с сохранением домена

Сохранить тот же домен/issuer обычно проще: клиентские URL и provider subjects остаются прежними. Полный перенос всё равно требует проверки восстановленной копии.

1. Зафиксируйте source revision, image IDs, ordered overlays и ресурсные/сетевые настройки обеих установок — приложения и входа.
2. Сделайте проверенные backups обеих БД: application PostgreSQL и identity PostgreSQL. Нужны **также** оба приватных state-каталога: `installation.json`, `runtime.env`, `compose.env`, encryption keyring, database/IdP secrets и provider recovery metadata. Одна SQL-копия не заменяет encryption/identity recovery material.
3. Подготовьте отдельный новый хост с теми же проверенными версиями. Абсолютные пути в метаданных закреплены: при восстановлении сохраняйте их или используйте отдельную проверенную процедуру адаптации профиля; простое перемещение каталога вызывает отказ `Load`. Убедитесь, что private subnet не конфликтует с новой сетью.
4. Остановите записи/worker/публичный ingress старого экземпляра для согласованной финальной копии. Старый и новый независимые writer не должны одновременно считать себя одним экземпляром.
5. Восстановите БД в выбранные отдельные volumes, state и file permissions. Без запуска обычных worker/public ingress проверьте миграции, записи, encrypted connections, provider realm/subject/client и маршруты TLS. Не выполняйте `init`, bootstrap или импорт начальных аккаунтов поверх восстановленного active provider.
6. Учтите, что восстановление старого backup может вернуть ранее отозванные полномочия. Примените собственную процедуру quarantine/revocation и проверьте её до открытия доступа. `recovery metadata/prepare/quarantine` — низкоуровневые примитивы, не автоматический координатор переноса.
7. Переключите DNS A/AAAA на новый сервер, выпустите/перенесите законный сертификат выбранным способом, проверьте `/health/ready`, OIDC discovery, sign-in, CLI/MCP, source synchronization и recovery. Старый хост сохраняйте как согласованный rollback target до приёмки.

Это операторская процедура, не обещание автоматического migration wizard. Автоматические тесты проверяют изолированные backup/restore и routing primitives; конкретный межхостовый перенос требуется проверить на ваших восстановленных данных.

## Смена домена существующей Gitmora

Домен участвует в публичном URL, certificate/SNI, nginx, provider `hostname`, OIDC issuer, client redirect URI/web origins, private host mapping и namespace CLI credentials. Одного изменения `WORKGRAPH_PUBLIC_URL` или DNS CNAME недостаточно.

Для **нового** экземпляра все значения задаются при установке. Для существующих данных заранее спланируйте новую identity-политику: новые точные issuer/subject bindings должны указывать на прежние локальные UUID после подтверждения провайдером. Не связывайте аккаунты автоматически по email/имени. Старые browser/CLI grants могут быть отозваны при смене fingerprint политики; пользователям понадобится вход на новый `--server`, обновление MCP-аргументов и контролируемая перепривязка collector-конфигурации.

Нынешние `deployment init` и `identity-server init` намеренно отказываются перетирать существующие профили. Не редактируйте issuer в приватной БД и не подменяйте ID ради обхода проверки. При необходимости сохранить существующую историю сначала отрепетируйте отдельную процедуру переноса на копии; новая установка с новым доменом поддерживается штатной инструкцией, смена identity существующей базы не является одной env-командой.
